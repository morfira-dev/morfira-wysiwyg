# Product roadmap

Status: revised development plan. SDK phase 1, P1–P3 behavior presets, U1/U2 modern UI and the first optional checklist/horizontal-rule slices are implemented locally. U3a opt-in group-priority overflow is implemented and verified under `editor-ui.md`; wrap stays the compatible default. U3b contextual text formatting and independent U3c caret-link, U3d selected-image and U3e table structure controls are implemented under their contextual specifications; current executed validation is recorded separately below and in the verification record. Expanded link/whole-figure/caption contexts remain future work. Remaining milestones describe priorities and acceptance outcomes, not release dates. SDK boundaries follow `specs/plugin-sdk.md`. Current verification results, generated bundle measurements and remaining evidence gaps are recorded in [verification-backlog.md](verification-backlog.md).

Morfira is an independently implemented strict-TypeScript editor under MIT. The product target is a ready everyday-authoring experience close to mature editors in common tasks, with measurable improvements in selected bundle size, extension contracts, UI and documentation. CKEditor, TinyMCE and notectl are comparison references, not implementations to copy. Feature-for-feature enterprise or office-suite parity is not required. Heavy conversion, collaboration and processing remain optional integrations for explicitly requested use cases, outside core. Core/plugins retain zero runtime dependencies; adapters use optional framework peers.

Every milestone follows specification → implementation → browser acceptance → size measurement → RU/EN documentation. Test a defined task/profile before claiming an advantage; smaller JavaScript does not prove faster input, lower history memory, complete accessibility or better compatibility.

The new bounded list-item replacement and boundary-deletion paths support direct-inline content or several ordinary paragraphs/headings per item. Replacement retains unselected body blocks; wrapped-body Enter splits the item and moves following blocks/branches, while Shift+Enter stays inside a body. Interior Delete/Backspace joins adjacent bodies. These paths are implemented locally; semantic body wrappers and mixed text/block shapes remain outside this slice; interleaved branches have only the separate structural quote-crossing profile below. Contracts follow `list-selection.md` and `lists-toolbar.md`; current browser, build, type and bundle evidence is recorded in [verification-backlog.md](verification-backlog.md). Evidence for a bounded profile does not imply arbitrary structural editing support.

## Milestones

Single ordinary quote HTML insertion is implemented locally for list carets and supported selections, retaining prefix and suffix bodies around the standalone quote. Quote content accepts inline data or ordinary paragraph/heading children. Repeated block paste in ordinary bodies preserves unselected validated quotes before/after the insertion. Inside one ordinary quote, multiple paragraph/heading payloads or a single heading compose inside the same wrapper at its caret or across child bodies. Structural paste crossing or covering one or more ordinary quotes in a single item is implemented locally, including endpoints in different quotes: incoming wrappers remain item-level siblings, partial quoted edges retain their actual wrappers, fully covered quotes/bodies are removed, and an unquoted caret paragraph precedes a quoted suffix. Every affected quote passes strict source validation. Structural quote crossings across consecutive sibling items are also implemented locally: retain the actual first item and move the actual right suffix, following bodies and last trailing branches under it; trailing branches from all selected items are retained as actual subtrees after all result bodies, ordered first→intermediate→last without coalescing; earlier branches are deliberately relocated after the body sequence. The extension is limited to structural quote crossings; native/no-affected-quote paths keep earlier branch barriers. For selected items containing wrapped blocks after lists, a separate ordered quote-crossing profile preserves prefix order, interval branches between incoming payload and suffix, and the exact following body/list sequence; the trailing-only profile is unchanged. Structural insertion inside one direct quote in an interleaved owner also reuses inner composition at a caret or selected range, preserving the full outer sequence and validating owner branch roots. Cross-list/level/branch endpoints, native quote boundary editing, nested structural quote content and semantic block payloads remain later work. Acceptance scenarios, bilingual examples and current validation are tracked in [verification-backlog.md](verification-backlog.md).

Single ordinary heading HTML insertion is implemented locally for list carets and supported selections: prefix body → preserved incoming heading → suffix body, with the caret before the suffix. It preserves item/branch structure and has atomic semantic/malformed heading barriers. Its contract is `list-selection.md`; current validation and generated sizes are recorded in [verification-backlog.md](verification-backlog.md).

The local list-paste extension accepts at least two ordinary paragraph/heading payload blocks over supported list selections and at a collapsed caret within a supported item. It retains prefix/suffix formatting, unselected blocks and branches within one item and one history operation. Item-level caret boundaries resolve to the following body start or final body end. Pending caret formatting participates in undo without leaking into the new insertion point. Structural and semantic multi-root payloads remain outside this slice. Current validation and generated sizes are recorded in [verification-backlog.md](verification-backlog.md).

The local first-body Backspace extension joins a previous item's final body or removes one list level for a first item, preserving multi-block bodies, trailing branches and subsequent items. Nested lift also supports a nonfinal owner branch: later validated branches move after the lifted item's own branches and source siblings, preserving depth-first order; earlier branches remain with the owner. Its specification is `lists-toolbar.md`; test coverage, RU/EN examples and current validation are tracked in [verification-backlog.md](verification-backlog.md).

## Size profiles and comparison rules

On 2026-11-18 the user approved increasing the standard JS guard from 65000 to 80000 gzip bytes to retain useful feature headroom. At the last measured 64602-byte largest selection this provides 15398 bytes of reserve instead of 398. Extended, core, optional-entry, adapter and CSS limits, zero-runtime-dependency/tree-shaking rules and compression/accounting remain unchanged. See editor-presets.md P4. Historical measurements and their original guards below are retained.

All sizes below are decimal bytes. Raw means minified JavaScript/CSS, not package archive size. Measure gzip and Brotli separately and count each shared chunk once per selected closure. Framework runtimes, source maps and declarations are excluded; fonts and additional locale alternatives are separate resources.

| Profile | Target or guard | Status |
| --- | --- | --- |
| Core | 80000 raw JS bytes | Working development target |
| Core | 200000 gzip JS bytes | User-directed product hard guard |
| Table / optional entry | 150000 gzip JS bytes | User-directed product hard guard |
| Each adapter | 10000 raw JS bytes | Existing enforced hard guard, framework excluded |
| Standard editor with selected plugins/UI | 80000 gzip JS bytes | Active measured-profile guard, headless and ready |
| Extended selection | 110000 gzip JS bytes | Active measured-profile guard, headless and ready |
| Standard/extended CSS | 20000 raw CSS bytes | Active selected-profile guard, headless and ready |

P4 guards are active in `scripts/size.ts` for the measured standard/extended closures; `editor-presets.md` records the lightweight-product reason and profile boundaries. Minimal remains measured without an additional preset guard. A preset must publish its actual feature list and resource/loading boundaries. Do not equate competitors' full distributions with a minimal local core or treat different feature sets as a functional parity benchmark. Tightening guards requires an explained product reason and a measured profile; writing a future target does not change build limits by itself.

## Delivery limits

Current tests do not certify arbitrary Office documents, every mobile/IME input path, accessibility conformance, memory-leak freedom or production readiness. New public API/document changes require explicit compatibility notes and migration decisions. Publication, deployment and Git writes remain separate user-authorized actions; the documentation site remains local-only.
