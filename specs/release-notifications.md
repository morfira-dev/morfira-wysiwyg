# Aggregated Telegram release notification

Status: initial live notification verified in GitHub run 44336166347 on 2026-11-18 and confirmed received by the user. The user now requests per-package changes with commit labels. Local tests/builds/type checks/dry runs remain disabled at the user's request; validation runs in GitHub CI.

Use pinned dev-only @nuykon/semantic-release-tg-bot 1.0.0. It is not imported by library packages or browser builds. Private workspace/release tooling requires Node >=22.20; public editor package runtime contracts are unchanged.

Do not add Telegram hooks to each package's semantic-release configuration. Instead run one optional notification step after a successful live multirelease and release-state persistence. It invokes the plugin's verifyConditions/success API once with a bounded HTML summary of only the packages actually released. Group changes by the independently versioned package, retain Conventional Commit labels/scopes/breaking markers and link each shown hash to its GitHub commit. Intersect semantic-release's returned commit list with the hashes touching that package's directory between its result's lastRelease.gitHead and nextRelease.gitHead (the initial release starts from repository history). The final result can retain repository-wide commits despite filtered analysis hooks; do not rely on its ownership or scope-based guesses. Dependency-only releases have an explicit internal-dependency explanation, not duplicated core changes. Ignore merge subjects and the generated version-sync commit. Other untyped subjects may appear under the neutral `commit` label. Do not include commit bodies, authors/emails, secrets, raw Markdown/HTML changelogs or arbitrary supplied URLs. Escape all interpolated text and generate links only for this repository with validated hashes/names/versions.

Preserve release-plan.json's existing shape for planning. A separate ignored release-published.json envelope retains version=1, sourceSha, runId, runAttempt and packages [{name,version}], with additive optional changes [{hash,label,subject}] and changeCount on each package. Older version-1 reports without these fields remain readable and say that details are unavailable. Retain at most twelve sanitized subjects per package (240 UTF-16 units each) and the total count, deduplicate hashes and bound label length. Validate report size at 256000 bytes, at most 32 packages, bounded strings and counts, and SHA syntax before any network call. Clear stale reports when release/planning starts. Produce it only after live publication, state persistence and plan writing all succeed, with nonempty actual releases. No-release and dry-run execution leave no live report; partial/failed publication never creates one. sourceSha is the pre-persistence commit and is compared with GITHUB_SHA, not HEAD after the version-sync commit.

Keep one combined message. Allocate visible space across packages fairly: select commits round-robin, cap displayed subjects at 120 UTF-16 units, retain omitted-change counts and a per-package release-notes link. Build HTML and its visible-text counterpart together; enforce at most 3800 visible UTF-16 units (below Telegram's 4096-character post-entity limit) and 32000 HTML source units. Never truncate escaped markup or a URL. Exceptionally many/long package headers that cannot fit even without commits fail the optional notification visibly. A failed/no-release run must not fabricate changes or send a retrospective success notification. Acceptance regressions cover actual package ownership, dependency-only releases, HTML/control-character handling, truncation with all package versions retained, invalid report metadata and compatibility with older reports.

The sender runs only in GitHub Actions on refs/heads/main. It requires matching current source SHA, run ID and attempt in a valid bounded report. No report/no releases/no complete Telegram configuration means no network or plugin import. Successful whole-workflow reruns that release nothing therefore send nothing. One invocation is not an exactly-once guarantee after a network timeout or explicit re-execution; there are no delivery retries or remote deduplication claims.

GitHub secrets: TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID; optional TELEGRAM_BOT_PROXY supports the plugin's HTTP/HTTPS CONNECT transport. Pass only these secrets to the plugin, only in the post-publication step. For private messages the user must first start the bot and provide the numeric private-chat ID; public channel usernames are supported by Telegram. No tokens or authenticated proxy URLs belong in files/logs/chat. Error output is bounded and redacts configured secret values.

The workflow notification step has success-only execution, a two-minute timeout and continue-on-error. Notification failure produces a visible warning without marking already-published npm versions as rolled back or repeating publication. Existing required checks, OIDC permissions and publication concurrency are unchanged; do not widen continue-on-error to the publication step. CI planning and PR jobs have no Telegram credentials and send no messages. No real Telegram send is part of this local integration.
